# Test data policy

**Never commit patient data.** This repository is public. A DICOM file from a
clinical system contains protected health information even when the obvious
tags have been blanked: UIDs, dates, private tags, burned-in annotations and
the image itself can identify a person.

## What is allowed

1. **Synthetic data generated by code.** This is the default and what every
   automated test uses. Generators produce small CT or MR series, RTSTRUCT and
   RTDOSE objects in memory, with fixed UIDs and seeds so output is the same
   on every run. They live in `packages/testdata` (issue #14).
2. **Clearly shareable public data**, only when a synthetic case cannot do the
   job. It must come from a public collection whose license allows
   redistribution, and the source and license must be written down next to
   it. It is downloaded when needed and is not committed.

Anything else is not allowed, including "anonymized" exports from a clinical
system, vendor sample files received under an agreement, and screenshots that
show patient identifiers.

## Rules for tests

- Unit and end-to-end tests build their inputs with the synthetic generators.
  A test never reads a DICOM file from the repository.
- Synthetic patients have obviously fake names and identifiers (for example
  `SYNTHETIC^PHANTOM`, `SYN-0001`).
- Local sample data goes in `/data` or `/sample-data`, which are ignored by
  git, as are all `*.dcm` files.

## CI guard

CI fails when a committed file looks like DICOM: a `.dcm` extension, or the
`DICM` marker at byte 128 (issue #14). The check has an allow-list for the
rare public file that must be committed; adding to it needs the source and
license in the pull request.

## If patient data is committed by mistake

Tell the maintainer immediately and privately (see
[SECURITY.md](../SECURITY.md)). Deleting the file in a new commit is not
enough: the history must be rewritten and the data treated as disclosed.
